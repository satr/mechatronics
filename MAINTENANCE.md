# Maintaining and extending this curriculum

This repository is **self-contained**. These instructions work after a clone or fork and do not depend on access to an author's chat history, private documents, connected accounts, or personal memory. An AI assistant or human contributor can start with this file, [AGENTS.md](AGENTS.md), the [English course index](docs/en/README.md), and the current lessons.

## Learning path and scope

When one chapter uses multiple synthetic models, **state explicitly when the underlying function changes**. In the motion-calculus chapter the derivative example uses x(t)=2t² with v(t)=4t, while the integration example deliberately uses v(t)=2t and x(t)=t²+C. Omitting this transition in translations implies a false derivative/integral identity and removes the reasoning chain. Locale-discovered tests should retain both models together in the integral section; do not rely only on matching final numerical results.

Explain a concept only after introducing the physical quantities it uses. Develop the lessons in this order: concrete motion → derivatives and integrals → numerical integration → first-order dynamics → rotation/torque/energy → later topics built on the same foundations. The order in [docs/en/README.md](docs/en/README.md) is canonical. Planned topics are not presented as already completed or independently validated.

For the planar 2R Jacobian, preserve the entire chain from four partial derivatives through the determinant product rule, cancellation of terms containing `L2²`, and the sine-difference identity. Link the original two-joint velocity-vector SVG and its numerical example in every locale. Avoid duplicated singularity explanations in condensed translations. Structural math tests do not replace native-language review.

**Current 13-language rollout (2026-11-15):** All 13 maintained editions have chapters 00–06, the derivative and integral references, trigonometry, symbol guides, short formula sheets, exercise instructions, same-page navigation and safety/licensing summaries. The original English placeholders in the nine established translated derivative tables were replaced with localized explanations and translated rule conditions. Automated locale-discovered checks now compare derivative equations, domain math, worked examples and reciprocal navigation across all 13 editions. Historical status notes below describe intermediate stages of the rollout, not today's missing content. Neither those tests nor this completion statement imply independent native-speaker proofreading: mathematical wording and naturalness still deserve editorial review.

## Runtime verification claim policy

Markdown link validation must ignore example syntax inside inline code spans (single or multiple backticks), as well as fenced code. Link and image destinations outside code still need to be resolved and checked for security issues. Without this distinction, explanatory syntax can look like a broken file link even though no such link is rendered. The helper is a source-level approximation, not a complete CommonMark parser.

Markdown security checks must cover parenthesized inline link destinations, colon-style reference definitions, and angle-bracket autolinks; checking only the first form permits reference-style URLs to bypass the source audit. This includes Markdown in notebook cells, which must reject embedded media HTML and unsafe `data:`/`file:`/`blob:` destinations. These are conservative source-string checks, not a complete renderer/parser sanitizer; keep user-facing documents and notebooks passive and test accepted local relative links.

The learner-example AST checker must reject forbidden scientific file I/O both as attributes (`np.load`) and as direct renamed imports (`from numpy import load as reader`). For `ast.ImportFrom`, inspect the original imported symbol, not only the alias, and reject blocked or dunder names. Positive math-function imports should remain possible. This is limited static detection; it does not establish safe dependency behavior or stop all Python indirection.

For PID teaching examples, retain the dimensional derivation of each gain in every language. In particular the measured speed error has units rpm, its time derivative has rpm/s, and a D current command in A therefore needs `K_d` in A·s/rpm. Do not preserve only the numerical 8 rpm / 0.01 s = 800 rpm/s example while dropping the gain's units or the reason for them. Locale-discovered parity tests cover all three pieces.

For the explicit Euler example of a first-order response, when `0 < dt/tau <= 1`, use the algebraically identical convex combination `(1-dt/tau)*v + (dt/tau)*target`. Unlike the naive `target-v` difference it can remain finite for large opposite-sign finite speeds. If `dt/tau` underflows to zero, do not discard a potentially representable change: evaluate the endpoint contributions as `(target/tau)*dt - (v/tau)*dt`. For `dt/tau > 1`, preserve the difference-based overshooting Euler step when the intermediate subtraction is finite: multiply by the already computed finite ratio `dt/tau`, rather than multiplying the difference by a huge `dt` before dividing by `tau`. If the ratio itself overflows, retain the staged multiplication as a possible finite fallback for tiny differences. Use the equivalent affine form only if the subtraction overflows. Neither route guarantees correctness beyond floating-point limits; include extreme numerical tests and distinguish intermediate overflow from a genuinely non-finite update.

For core exercises and notebook Python cells, importing NumPy/Matplotlib is for synthetic numerical calculations and visual display, **not local file access**. The AST checker rejects known scientific I/O APIs such as NumPy load/save/fromfile/memmap and Matplotlib imread/imsave/savefig as direct attribute references. The reviewed graph-generation tools are separate maintainer-only scripts and are not covered by the learner-example AST policy. Static AST inspection remains susceptible to dynamic indirection and dependency internals: maintain review discipline and never describe the examples as sandboxed.

The single optional Jupyter teaching notebook must keep a minimal Python 3 kernelspec (`name=python3`, `language=python`), supported top-level keys, and empty per-cell metadata. Reject unexpected extension metadata, attachments, saved outputs or execution fields on Markdown cells. The checker reads notebook JSON and code cells as data, but users opening notebooks still trust their local Jupyter installation and dependencies; this is not a sandbox.

The trusted-base PR audit should fetch **changed Markdown and SVG as data** as well as Python and notebook sources, applying the base branch's passive-content checks without importing or rendering submitted files. This helps prevent a PR that edits the ordinary validator from silently bypassing Markdown/SVG policy before merge. The read-only audit still relies on repository rulesets and independent review for sensitive workflow/tool changes.

Static media and Markdown are untrusted inputs too. Keep original SVG teaching diagrams passive: no DTD/entity declarations, active SVG elements, external href resources, inline event handlers, stylesheet imports or nonfragment CSS fetches. Matplotlib can emit an external SVG 1.1 DTD by default; remove this when regenerating plots. Source Markdown must not include embedded media, active HTML, raw HTML resource/style attributes, or unsafe URL schemes such as `javascript:`, `data:` and `file:`. Use normal Markdown links for reviewed external references; safe fragment anchors and examples in code fences are permitted. Source-only checks are defense in depth, not viewer sanitization or a substitute for human review. Permit a standard XML declaration in passive SVG, but reject XML processing instructions (including XML stylesheet references); matching only the prefix of 'xml-stylesheet' as a declaration is not sufficient.

The live ROS 2 Docker workflow invokes a repository Bash script and the host Docker daemon: do not execute untrusted pull-request inputs on the host runner. Automatic live smoke runs only on pushes to `main` affecting `ros2/` (or the workflow), and manual workflow_dispatch is guarded to `main`. This leaves PRs without premerge live ROS results; independent review before merge and postmerge CI confirmation are distinct requirements. Do not treat passing ordinary Python PR checks as successful ROS graph execution.

The normal `validate.yml` Python tests execute repository code only inside a non-root Docker container with networking disabled and the source mounted read-only. This is CI risk reduction, **not** proof that a submitted PR is harmless: the upstream Python image is mutable and the separate ROS Docker workflow executes untrusted build inputs. The trusted-base audit reads changed Python examples as data; any changes to tests, tools, or workflows still require independent review and enforceable repository settings.

Do not confuse the ordinary offline Python CI job with the separate real single-container ROS 2 Docker smoke workflow. The latter actually starts two application nodes, receives a typed topic message and calls a Trigger service on GitHub Actions; it does not prove compatibility with the learner's Docker installation, multi-host DDS, deterministic latency or hardware. When a test workflow is introduced or its scope changes, update the canonical English chapter and **every** supported translation before repeating verification claims. Link the concrete workflow and describe the observable assertions, not a vague claim that CI either tested everything or executed nothing.

## tf2 versus URDF/state-source semantics

In ROS 2 tf2 explanations, state the parent-child transform direction precisely: a parent `base_link` / child `tool` translation of +0.1 m along parent X with identity rotation puts the tool origin at +0.1 m in the parent; the reverse origin in the child is -0.1 m. **Only when rotations match** is reversing a transform equivalent to negating translation. For rotated frames use the exact inverse `p_child = R^T (p_parent - t)` and `t_inverse = -R^T t`; show a complete numerical +90° counterexample. ROS geometry conventions use metres for translation, unlike the independent coordinate chapter's millimetre examples. tf2 changes do not command motion and do not replace timestamp checks.

Keep the worked W → T → S composition in coordinate-frame chapter 04 complete across translations: a +90° rotation of T, its (100 mm, 50 mm) world translation, the (20 mm, 0 mm) sensor offset in T, the order `T_WS = T_WT T_TS`, and the (0 mm, 10 mm) sensor point mapping to (90 mm, 70 mm) in W. Rotation entries are dimensionless, translations are in mm, and the homogeneous 1 is dimensionless. The companion ROS 2 tf2 chapter addresses time-stamped transform infrastructure, not a replacement for the matrix mathematics.

When explaining coordinate transforms, distinguish named frames from moving body geometry and preserve the **measurement timestamp**. A tf2 query of a camera observation requires a connected transform chain at the observation time; latest pose is not always appropriate and missing/extrapolated data must be handled explicitly. A URDF model specifies fixed/movable joints, while `robot_state_publisher` combines the model with `/joint_states` to publish transforms. A model does not synthesize missing sensor readings or implement forward/inverse kinematics, collision checking or a safety controller. A hypothetical `map → odom → base_link → camera_link` chain is a teaching example, not a mandated ROS topology.

## How to make a substantive addition


**Completeness check for independent chapters:** A reference lesson is not a chat exercise. Before publishing, replace personal or open-ended coaching prompts with neutral worked examples showing the problem, assumptions, intermediate steps, answer and interpretation. Explain where angles and coordinate frames are measured. If a spatial relationship matters, supply an original, accessible diagram with the correct geometry. Keep all supported language editions equally complete; maintain rendered images and automated checks. Interactive unanswered questions belong in coaching conversations, not public-ready chapter content.

1. **Choose its natural place.** Extend a current lesson when the topic is an explanation of an existing formula, or create the next numbered lesson when it needs a separate prerequisite. Do not append chronological chat transcripts or personalized progress records.
2. **Write and check the English edition.** Begin with an intuitive explanation, define variables and units, show a small example, and provide a short explanation *at the first point a non-obvious result appears*. Non-arbitrary numbers must link to a calculation, derivation, or credible source. Put long derivations and edge cases at the **end** of the lesson and link to them from simpler sections using permanent explicit anchors.
3. **Synchronize every supported translation** (discover the current set under `docs/`). Match mathematical meaning, assumptions, sample values, anchors, examples, chart references, warnings, and section order. Translate text **inside formulas** when prose words are used there (for example `\text{平均速率}`), not only explanatory paragraphs. Add the English technical term in parentheses at the first appearance of a localized technical term; do not replace the localized term with English.
4. **Use numbers and units consistently across all languages.** Use a period as the decimal marker (`0.5`, `3.8`, `63.2%`) even in editions whose ordinary prose traditionally uses a decimal comma. SI unit symbols are language-independent, upright, case-sensitive and not translated; translate full unit *names* as needed while supplying English equivalents at first mention. For Chinese/Japanese also include the local name and the international SI symbol on first mention. Insert a space between a numeric value and a unit (`1 s`, `4 mm`, `10 mm/s`). Use a centered dot `·` or `\cdot` for unit multiplication (`kg·m²`, `N·m·s/rad`), not a comma, and do not put spaces around a slash in compound units (`mm/s`, never `mm / s`). Avoid the thin-space LaTeX command `\,` in beginner-facing formulas because it has been mistaken for a printed comma; use `\ ` for a visible separation. Write differentials upright as `\mathrm{d}t` and distinguish them from the numerical step variable `dt`. Check dimensions and render equations, not just source text. The BIPM SI Brochure permits either decimal point or comma; the decimal point is this repository's editorial choice.
5. **Maintain pictures as reusable sources.** Prefer original mathematical plots, SVG diagrams, or Mermaid with a source file and clear variable labels so all supported languages can share the same figure. Use a localized caption and accessible alternative text. Never copy copyrighted charts without the necessary rights and attribution. Figures are explanatory, not operational control schematics.
6. **Use lists for scans.** Do not place long sequences of terms or related items in one prose line. Prefer bullet lists (or compact tables for structured comparison); one item per line in every supported language edition. Review how the Markdown actually renders, not only its source.
7. **Verify formatting.** GitHub-flavored Markdown (GFM) treats raw vertical bars inside a table cell as column separators, including bars inside `$...$`. Use `\lvert` and `\rvert` for mathematical absolute values in tables. Use `$...$` for inline math and separate-line `$$` for display math. Prefer rendered GitHub formulas with standard LaTeX; avoid invented macros and bare LaTeX outside math delimiters.
8. **Update navigation and references.** Maintain a TOC in substantial chapters; verify headings, anchor links, figure paths, locale-specific links, the cheat sheets, README indexes, and any glossary entries. Treat the English version as the reference, but independently check translation accuracy and readability.
9. **Keep only public-safe, properly licensed content.** Never add candidate names, private learning plans, interviews, academic applications, private resource URLs, email addresses, personal logs, private screenshots, credentials, or biographical clues. Use synthetic values, neutral filenames and generic commit messages. Check the full diff and file metadata, not just the prose.
10. **Run tests before publication:**

   ```bash
   python3 -m unittest discover -s tests -v
   python3 tools/validate_repository.py
   ```

   If graphs or formulas change, also run `python3 tools/generate_figures.py` with Matplotlib installed and review the generated SVGs visually.
11. **Commit and confirm.** Commit validated changes in GitHub, reread key files and the repository tree, and describe what changed, without claiming that external reviewers have approved it. If the GitHub write is unavailable, preserve a local patch or archive; do not pretend that a commit happened.

## Common clarity traps already encountered

- If `x(t)=2t²`, write immediately why `dx/dt=4t`: `d(t²)/dt=2t`, then multiply by 2. Explain the coefficient's units and link to the complete derivation.
- If stating that a first-order system completes 63.2%, 86.5%, and 95.0% of a step after one, two, and three time constants, link to the formula `1−exp(−t/τ)` and show its evaluation in the appendix. These numbers are calculated, not fitted by convention.
- If using a toy proportional-torque motor model, distinguish the drive command from the actual motor torque and specify when `τ=J/K` applies. Inertia is not a friction force.
- Do not confuse a simulation step `dt` with a model's physical time constant `τ`, or equal velocity responses with equal torque and energy requirements.
- In PID/PI worked examples, distinguish accumulated integral, proportional contribution, integral contribution and signed **total** output. Verify the complete command, including changes in sign and the effect of saturation. Do not explain only the integrator when example code computes the complete controller output.
- Translate safety-critical notices in every locale: a translated label followed by an English-only warning is not a valid localized warning.
- Translate *model-specific assumptions and applicability limits* near the start of each corresponding lesson; a generic disclaimer about errors or safety is not a replacement for physical model assumptions such as neglected friction or saturation.
- Compare translations concept by concept, not merely by matched heading IDs and equations. Preserve exact versus approximate relations, domain assumptions, intermediate transformations, sign/direction explanations, boundary exceptions, and complete numerical substitutions in worked examples. For the single rotating link, distinguish exact arc length, signed arc distance, chord displacement, average path speed and the instantaneous limit.
- Prefer direct explanations over academic-sounding language. See [Writing style](WRITING_STYLE.md).

## Mathematical notation and executable examples

For a first-observed 63.2% threshold estimate, the declared sensor quantization resolution must be strictly smaller than the magnitude of the input step. Otherwise the change is not distinguishable at the declared resolution and the quantization half-step margin can invent a crossing at the initial sample. A larger measurement uncertainty calls for more informative data or a different system-identification method, not a falsely precise tau. Preserve the existing overflow-tolerant behavior for extremely large finite endpoints; test rising/falling examples.

Numerical evaluation order affects underflow and overflow. In the synthetic rotational energy expression E=0.5*J*omega**2, halving a **subnormal** positive J first may round it to zero even though E remains finite and representable for very large omega. For subnormal J, multiply J by omega before the half-omega factor; retain the existing evaluation order for normal J, because it can avoid spurious overflow in other valid cases. Test both underflow and near-range limits. This is a floating-point demonstration, not a plausible physical rotor specification.

When illustrating a finite-difference derivative, shrinking dt indefinitely is NOT always beneficial: on floating-point data, t+dt may equal t, or separate positions may both underflow to zero. For the synthetic x(t)=2*t^2 exercise, raise a clear precision error instead of silently reporting a false zero, while preserving a genuine zero secant across symmetric sample points. Keep the direct finite-difference method visible so students can compare it with the analytic derivative, and cover both error cases in tests.

For the synthetic time-constant sample estimator, distinguish the **first sampled observation** crossing 63.2% from the exact physical crossing time: sparse sampling and known rounding resolution limit precision. Require finite measurements, nonnegative strictly increasing timestamps relative to the step, and validation of the complete list even after the first crossing. Do not return early before checking later bad data, and cap sample count to prevent unbounded local processing. Cover rising and falling steps in numeric tests.

For finite-step numerical examples, compare a duration to the integration step through the **dimensionless ratio** `duration / dt`. Do not use a fixed absolute time tolerance such as `abs(round(duration/dt)*dt-duration) <= 1e-9`: it can incorrectly accept non-integer step counts for intervals much shorter than that threshold. Bound the step count, reject nonfinite values, and test both tiny exact multiples and tiny non-multiples. This concerns synthetic numerical models only.

When giving planar direction from components, distinguish `atan(y/x)` (which loses the quadrant and is undefined when `x = 0`) from `atan2(y, x)` for nonzero vectors. Preserve signed coordinate examples, matching argument units, the undefined direction at `(0, 0)`, and explicit degrees/radians conventions across translated trigonometry pages. The numerical reference table needs independent sin/cos/tan/atan checks, not just column-count checks.

Within Markdown math delimiters (`$...$` and `$$...$$`), TeX commands need a **single literal backslash** in the repository's source: `\int v\ \mathrm{d}t`. Do not paste JSON-/Python-escaped strings containing a doubled backslash before `\int` or `\mathrm` into Markdown mathematics. Verify actual source characters rather than serialized API responses, and review GitHub rendering when practical. The introductory calculus table's two integral formulas are checked in every locale.

- Use **Greek `\varepsilon(t)` for a changing speed error**, never the letter `e(t)` when the same lesson uses Euler’s number. Define `\exp(z)=\mathrm{e}^{z}` and `\mathrm{e}\approx2.71828` at the FIRST use of the exponential response in every language. Use `\exp(-t/\tau)` throughout the mathematics, alongside `math.exp(-t / tau)` or `numpy.exp(...)` only in Python code.
- Prefer **rendered fractions** `\frac{a}{b}` inside `$...$` or `$$...$$` rather than `a/b` in mathematical explanations and formula tables. Python source must use `/`. Prefer one displayed equation per conceptual step instead of long combined lines when possible. Do not convert ordinary paths, code snippets, or SI unit names into math.
- Place the definition of a mathematical symbol before its first appearance. Present the exponential derivation and the 63.2%/86.5%/95.0% calculation as ONE connected explanation in an optional end-of-chapter section, and link to it from the introductory example. Do not repeat a similar half-explanation earlier and then introduce new symbols several pages later.
- Keep the core exercises as local standard-library Python files, without browser execution or external API calls, secrets, private data or physical actuator interfaces. Link the official Python installation and venv guides rather than third-party code execution services.
- Maintain concise local Python execution instructions in the root README and all supported exercise guides. On Windows use `py -3`; optional packages belong in an isolated `venv` and `requirements.txt`. Keep the notebook links and dependencies consistent.

In macOS/Linux instructions use `python3`; on Windows use `py -3`. Prefer the venv interpreter explicitly for optional package installations, and link official Python documentation. Keep all supported language editions consistent.

For the first-order response in calculus chapter 00, explicitly distinguish the zero-initial-speed special case from the general response with `omega_0`.
