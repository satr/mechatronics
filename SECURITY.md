# Security review and limitations

This repository is a synthetic teaching resource, **not a sandbox**, a verified software distribution, or code suitable for controlling machinery. In particular, [Docker daemon access can expose host privileges](https://docs.docker.com/engine/security/); a non-privileged Compose configuration reduces exposure but does not establish that arbitrary Dockerfile or upstream content is trustworthy. For engineering/physical safety see [SAFETY.md](SAFETY.md).

## What can execute?

- The standard-library scripts in `exercises/` execute only when explicitly run locally by a reader. The repository no longer ships a browser Python runner or Pyodide dependency. Review downloaded code before executing it; a local Python environment is not a malware sandbox.
- Maintained `.ipynb` files can also contain executable Python cells, regardless of their folder. The offline checker now parses their notebook JSON and Python cells **without running them**, rejects saved execution outputs and common active HTML/script-like markup, and reports non-allowlisted imports. This is an audit aid, not Jupyter isolation, and does not guarantee safety of library dependencies or notebook renderers. The repository deliberately accepts only the minimal `python3` kernel configuration and empty cell metadata; extra notebook metadata, extension-specific fields and attachments require an explicit review and policy update before inclusion.
- `ros2/Dockerfile` installs software from a ROS base image and Ubuntu package repositories, builds a Python package, and runs a synthetic ROS 2 graph. Its base image tag and package versions may move; neither Docker nor CI establishes full supply-chain integrity. **Pinning a base-image digest alone is insufficient** because `apt-get update` still installs changing package revisions. Verify dependency provenance and controlled repository/package versions before making stronger reproducibility claims; freezing versions also means maintaining a separate security-update process. See [Docker build best practices](https://docs.docker.com/build/building/best-practices/).
- GitHub Actions can execute code submitted in pull requests. The ordinary Python validator/test suite runs in a separate, network-disabled, non-root, read-only container rather than directly on the host runner. **The ROS 2 Docker smoke job does not run on pull requests**: it uses a host Docker daemon and a repository Bash script, so its automatic trigger is limited to changes pushed to `main`, with manual `workflow_dispatch` permitted only on `main`. This avoids direct host execution of *unmerged PR* Dockerfiles and shell scripts, but does not certify main-branch changes as safe: require independent review before merging. A PR cannot claim its ROS runtime passed the live job until that check actually runs after merge. Even a static AST checker cannot protect against malicious edits to itself, workflows, tooling, dependencies or tests in the same PR.

## Checks provided by the repository

The offline repository validator examines **all** original SVG figures for active SVG elements, unwanted DTD/entity declarations, external resource references, event attributes and non-local CSS URLs. It also rejects embedded media/active HTML, raw HTML resource/style attributes, and dangerous `data:`, `file:`, `blob:`, `vbscript:` or `javascript:` Markdown destinations outside code samples. The check includes reference-style Markdown destination definitions (`[label]: URL`) and unsafe autolinks, in addition to inline links; notebook Markdown uses conservative unsafe-media and URL markers even though Jupyter can render Markdown differently. The legacy Matplotlib-generated figures have their external DTD declarations removed. These checks are conservative signatures, not a full HTML/XML sanitizer, a secure viewer, or proof against every possible injection.

1. Run `python3 tools/check_executable_sources.py` before any executable-example tests. This **parses source without executing it** and rejects unexpected imports and common dynamic-execution, reflection, and filesystem-command APIs under `exercises/`, `ros2/demo_pkg/` and Python code cells in `notebooks/**/*.ipynb`. New Python files in those directories (including nested directories) participate automatically. This policy also rejects direct scientific-library file operations such as NumPy loading/saving and Matplotlib image reading/writing in lessons and notebook code, while permitting numeric and plotting APIs. The same forbidden entry points are rejected when brought into scope by `from ... import ... as ...`, so renaming `numpy.load` to another local name does not bypass the direct-call restriction. This is a conservative review aid, not a general malware detector; it cannot reason about dynamic aliases, third-party library internals, all possible Python bypasses or all effects of allowed APIs.
2. Run `python3 -m unittest discover -s tests -v` and `python3 tools/validate_repository.py` for numerical, structure, links, copy parity and text privacy checks. These checks **do execute repository code**. In CI the ordinary Python checks run inside a Docker container with `--network none`, read-only repository and filesystem mounts, a non-root user, dropped capabilities, resource limits and no explicitly forwarded GitHub token or secrets. This limits routine exposure but **does not certify hostile code as safe** or make Docker a perfect sandbox. The Python image `python:3.11-slim-bookworm` is a mutable official tag; pulling it introduces an upstream dependency that requires review.
3. CI has read-only GitHub permissions and uses pinned GitHub Actions commit SHAs; checkout uses `persist-credentials: false`. The host checks out source but does not run PR Python directly. Do not introduce privileged tokens, repository secrets or Docker socket mounts into a pull-request validation container. Never use `pull_request_target` to check out and run untrusted PR code.

## Automated dependency and security checks

- **CodeQL and Semgrep:** `.github/workflows/codeql.yml` runs CodeQL v4, while `semgrep.yml` uses the maintained Semgrep CLI. Both save SARIF reports as workflow artifacts, including while this repository is private. Upload to GitHub code scanning occurs only when the repository is public and permissions allow it. A green private job is **not** equivalent to successful GitHub code-scanning ingestion; review artifacts for findings.
- **Python dependency vulnerabilities:** `dependency-vulnerability.yml` audits the real root `requirements.txt` with pip-audit. Dependency Review runs for public pull requests; it may require paid GitHub security entitlements when the repository is private. `snyk.yml` scans the same root manifest using the `SNYK_TOKEN` secret only on trusted default-branch runs. Missing token is an explicit failure, not a skipped-success result.
- **ROS Docker images:** `docker-vulnerability.yml` builds both Dockerfiles on trusted `main`, then uses Trivy against the resulting installed OS/ROS/library packages. Fixable HIGH/CRITICAL vulnerabilities fail its job. Unfixed advisories are excluded from that gate; review them separately. This is a deliberately post-merge gate because Docker builds invoke a host Docker daemon and must not execute unreviewed PR instructions.
- **Unverified secret diagnostics:** `.github/workflows/secret-candidate-diagnostics.yml` runs once on its introduction to main and on explicit main-branch manual dispatch. It inspects unverified TruffleHog hits without storing or printing token candidates. The output is restricted to detector, file, line and whether the candidate exactly equals a pinned GitHub Action SHA. Treat other locations as potential exposure until reviewed privately. A clean verified/unknown-only CI job does **not** imply there are no unverified candidates.
- **Secrets and updates:** `secret-scan.yml` checks git history using TruffleHog; a zero-finding run is not proof of complete absence of historical private data. The CI failure gate reports verified and unknown results, not unverified heuristic candidates (which can include valid 40-character action commit SHAs); review unverified candidates separately during the publication audit. `.github/dependabot.yml` requests weekly Python, GitHub Actions and ROS Docker image updates through reviewed PRs.
- **Core validation:** `validate.yml` remains the canonical restricted CI and runs repository tests inside a network-disabled non-root container. The unrelated imported `ci.yml` was removed instead of introducing fake project extras and Makefile targets.

**Historical false-positive check (16 November 2026):** TruffleHog 3.90.8 reported three unverified `Github` matches at the pinned `github/codeql-action` SHA in `.github/workflows/semgrep.yml` and `.github/workflows/codeql.yml`. Both source lines reference the official upstream v4.39.3 commit; its SHA was independently checked against the GitHub release. TruffleHog 3.99.8 reported zero unverified matches on the same history. No confirmed secret was found. The old scanner was used only for a redacted diagnostic comparison; normal and diagnostic workflows now use 3.99.8.

**Before publication:** audit the full history, enable appropriate code scanning and security alerts after the visibility change, review SARIF/artifact findings, and configure branch protections, required checks and independent reviews where possible. Do not assume all private-repository security features are enabled or that a green job actually executed every scanner.

## Separate trusted-base PR inspection

The `.github/workflows/trusted-source-audit.yml` workflow uses `pull_request_target` strictly to **check out the base commit**, never the PR head, and has read-only token permissions. From the base commit it parses changed synthetic Python and notebook code plus source-controlled Markdown and SVG blobs fetched via the GitHub API. Submitted Markdown is checked for common active HTML and script URL patterns; SVG is inspected for external DTDs, active elements, external references and event attributes. **Submitted files are read as data, not imported, rendered or executed.** These conservative signatures do not certify the absence of malicious content. A PR cannot modify the checker that audits itself until its changes reach the protected base branch. Edits to security-critical tooling and workflows are reported for independent human review, not automatically certified safe.

This status becomes a meaningful **merge gate only if a repository administrator makes `trusted-source-audit` a required check** and requires independent review of sensitive source, test, tooling and workflow changes. It does not stop the ordinary `pull_request` validation container from running submitted Python tests; restrict approvals and credentials separately. The live ROS 2 Docker job is intentionally not a pre-merge PR check and runs only after a `main` push or manual dispatch on `main`.

## Required controls outside the repository code

Repository rules and review permissions must be configured by an administrator; a workflow or scanner changed by a PR cannot enforce its own trustworthiness. Before accepting third-party contributions:

- Require pull requests, passing checks, and an independent code review for changes to `tools/`, `tests/`, `.github/workflows/`, `ros2/` and `exercises/`. Configure a ruleset/branch protection so an author cannot unilaterally bypass these checks.
- Keep the default workflow token restricted to **read** permissions. Require approval of workflows from outside contributors, especially for changes containing executable code.
- Enable GitHub secret scanning and dependency/security advisories if available to the repository. Review Docker image updates and upstream package changes, not only Python source diffs.
- Verify downloaded/installed third-party artifacts and their origin before treating builds as reproducible. A versioned CDN URL is not an integrity signature.

If there is no second trusted reviewer, acknowledge the limitation instead of describing self-approval and CI as independent verification.

## Reporting

For a potential vulnerability, avoid publishing exploit payloads, access tokens, passwords or private data in an issue or commit. Prefer the repository's GitHub private vulnerability-reporting mechanism if enabled, or contact a trusted repository maintainer through an existing private channel.

Security checks and policies reduce risk; they cannot guarantee the absence of injected or malicious code.
